# Agent Note: 抽取可注入模型流的主轮执行器

Status: implemented

## Problem

`runTurn()`、工具准备与执行、模型请求和终端输出原本都在 `agent.ts` 中。导入该文件会直接启动 REPL，模型流又来自真实 API，因此同批结束工具补结果、循环守卫累计中止、纯文本请求预算和多个工具调用配对只能依赖人工或真实模型观察。

这些分支承担消息协议完整性和本轮退出条件。只测试 `detectRepeatedCall()`、`collectResponse()` 等局部函数不能证明主循环把它们正确组合；继续依赖真实模型又会受到模型选择、网络和中转服务差异影响。

## Decision

[turn.ts](../../../../src/turn.ts) 持有 `SYSTEM_PROMPT`、`runTurn()`、公共工具处理和本轮控制常量；[agent.ts](../../../../src/agent.ts) 只负责启动初始化、终端用户输入、跨轮历史裁剪、本轮 checkpoint 回滚、取消处理和 UI 释放。`runTurn(messages, options)` 保持直接修改传入历史的契约。

`RunTurnOptions` 允许替换模型入口、请求次数与输出：

- `createStream`：默认动态加载真实模型流，测试注入模拟流；导入 `turn.ts` 不要求 API 环境变量，也不会启动 REPL。
- `maxIterations`：默认上限为十，测试可以使用更小预算稳定构造耗尽分支。
- `write` 与 `log`：生产默认写终端，测试使用无输出或收集函数检查控制信息。

工具 schema 与准备使用主注册表的公共接口，批准和执行继续使用 `requestApproval()` 及公共执行函数，没有建立第二套工具模拟框架。主循环测试使用无需批准的控制或计算工具，直接检查真实消息数组、工具调用 ID 和下一次模型请求。

[turn.test.ts](../../../../src/turn.test.ts) 固化四类组合边界：`finish_task` 后同批剩余调用补“未执行”结果；连续相同调用累计两次命中守卫后补齐当前及剩余调用；持续纯文本达到请求上限且内部提示不产生真实用户轮；同一响应中的多个普通工具结果按各自 ID 回填并进入下一次请求。

## Alternatives considered

- 继续只做真实模型端到端验收：最贴近运行环境，但模型输出不稳定、速度慢且依赖 API，难以稳定构造罕见退出分支。
- 直接从 `agent.ts` 导出 `runTurn()`：改动较小，但导入模块仍会执行 `main()`，同时静态加载 API 与终端依赖；增加入口判断后，职责依旧混在同一文件。
- 在测试中复制一份简化循环：无需改生产结构，但只能证明复制品，最容易在后续修改时与真实主循环漂移。
- 为模型、注册表、批准、控制台和所有工具建立完整接口层：隔离最彻底，但会把学习项目推向通用框架；只注入确定性回归实际需要的模型、次数和输出，批准及工具执行仍复用现有函数。

## Consequences

主轮组合逻辑可以在不启动 REPL、不读取 API 配置和不请求真实模型的情况下稳定回放，结束工具、循环守卫、请求预算和多工具配对成为常驻回归。CLI 入口缩小后，本轮编排与跨轮历史、异常回滚的职责边界也更清楚。

代价是 `runTurn()` 新增了少量依赖注入接口，测试仍执行真实的无副作用工具实现；若工具注册表或控制工具产生全局状态，测试需要继续选择隔离良好的用例。批准流程仍依赖终端人工输入，模拟流测试不能代替兼容服务协议、模型选择和交互批准的真实验收。

## Verification

2026-09-20，学习者运行 `npm run typecheck` 通过，`npm test` 五十二条通过、零失败；AI 随后在当前工作区重新运行相同命令，结果一致。新增四条测试检查完整历史和调用 ID，而不只检查控制台输出。

真实模型普通请求调用 `calculate` 得到 `391`，输出结果后调用 `finish_task`。真实委派请求中，主模型先维护 todo，再调用 `delegate_task`；子 Agent 使用搜索和分段读取检查 `src/turn.ts`，在最终总结请求返回 `runTurn()` 的职责，主模型移除临时 todo、总结并调用 `finish_task`。两条路径均收到 usage，证明动态默认模型入口、工具结果回填和显式出口仍可工作。
