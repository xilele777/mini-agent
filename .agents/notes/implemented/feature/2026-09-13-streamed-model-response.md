# Agent Note: 流式显示与完整消息组装分离

Status: implemented

## Problem

原来的 `runTurn()` 等待完整模型响应后才显示文本。改为流式请求后，文本可以即时到达，但工具调用的 ID、名称和参数可能分散在多个片段中；不完整响应不能直接写入历史或进入工具执行流程。当前主轮入口见 [turn.ts](../../../../src/turn.ts)。

## Decision

[collectResponse](../../../../src/stream.ts) 单独负责消费一次模型流：文本和拒绝文本到达时调用显示回调，并在本次请求私有的 Map 中按调用 index 累积 ID、名称和原始参数字符串。函数只返回完整的 assistant message 与实际收到的 usage，不执行工具、不校验业务参数，也不写历史。

读取结束后，有工具调用时结束原因必须是 `tool_calls`，无工具调用时必须是 `stop`。缺少结束标记、截断、过滤、不支持的调用类型，以及不完整、跳号或重复的调用标识均作为协议错误抛出。返回的函数调用按 index 排序且必须从零连续；当前只支持一个回复候选和 function 工具。

完整响应中的非法 JSON 或业务参数保留原文，交给现有 [prepareCall](../../../../src/tools/index.ts) 解析和校验，再作为普通工具错误反馈给模型。协议完整性和工具契约校验因此保持为两层边界。

`runTurn()` 请求启用 `stream: true` 与 `stream_options.include_usage`。usage 在 choices 之前读取，以接收 choices 为空的尾部统计片段；终端文本由回调逐片输出，流正常组装后才将 assistant 消息加入历史并进入循环守卫、批准、执行和完成／暂停流程。接收异常继续沿用[本轮历史回退](../bug-fix/2026-09-06-tool-result-history-recovery.md)。

## Alternatives considered

- 在 `runTurn()` 内直接消费所有分片：接入时少一个模块，但协议组装会和批准、执行、循环守卫交织，难以单独回放失败输入。独立函数保留了现有消息结构，并允许用模拟流覆盖边界。
- 使用 SDK 的自动组装辅助方法：可以减少自维护协议代码，是扩展更多响应类型时可重新考虑的方案；当前项目以手写机制为学习目标，显式累积直接承接了已有练习。这里没有做性能对比实验。
- 参数一旦能解析就提前执行：可能缩短等待时间，但可解析前缀不证明响应正常结束，也不能确认其余调用及对应历史已完整。等待完整响应才能保持工具结果配对和异常回退边界。

## Consequences

文本可以在模型生成期间显示，同时历史、工具校验和执行仍只接收完整消息；多个同名调用和交错片段不会因名称相同而混合。协议异常与参数错误分开处理，使损坏的流不能触发工具，而模型仍有机会修正完整但不合法的参数。

代价是项目开始自行维护一部分流协议，只覆盖单个回复候选与 function 工具。兼容服务若改变结束原因、调用编号或 usage 尾片行为，需要更新组装器和测试。接收中途失败时，已经显示的文字无法撤回；历史回退也不能撤销此前已经发生的外部动作。

阶段 8 的三个独立练习脚本在正式组装器和常驻测试接入后删除，避免教学脚手架成为第二套实现入口；练习证据保留在[学习进度](../../../learning/progress.md)。
