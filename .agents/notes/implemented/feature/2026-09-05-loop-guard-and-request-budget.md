# Agent Note: 用请求上限和连续重复检测限制失控循环

Status: implemented

整理日期：2026-09-11。文件名日期的依据见 Verification。

## Problem

模型可能重复发起没有新信息的调用，或在纯文本说明与内部继续提示之间反复切换。只依靠模型自己判断何时结束，无法为一次用户输入限定工作量。

## Decision

每次真实用户输入的主轮与摘要默认最多发起十次逻辑模型请求，内部继续提示后的请求也计入。主／子／摘要的实际传输及重试另外共享[全轮运行预算](../architecture/2026-09-22-runtime-resilience.md)，局部次数不能绕过总额。另记录本轮函数调用请求，连续三次工具名和原始参数字符串完全相同时，拦截当前调用并回填守卫说明；累计触发两次后结束本轮。

记录的是请求，不只已成功执行的动作，因此参数错误、拒绝和守卫拦截的请求也会参与检测。守卫早于参数准备和批准执行；它不能替代[明确的完成与暂停出口](2026-09-11-explicit-turn-exits.md)。

## Alternatives considered

- 只设固定请求上限：能够最终停止，但同样动作可能在停止前重复执行很多次。
- 只检测重复调用：能识别局部循环，但参数变化或纯文本复读仍可能无限继续。
- 按语义相似度判重：可以捕捉更多重复，但也可能误伤合法探索，并需要定义额外的不确定阈值；当前采用可解释的逐字比较。

## Consequences

失控循环有明确的本轮停止条件，代价是阈值固定，合法重试也可能被拦。改变 JSON 空白、键顺序或穿插其他工具会绕开连续相同判据，不能称为完整循环证明。

结束前仍需遵守[工具结果配对与历史恢复](../bug-fix/2026-09-06-tool-result-history-recovery.md)；提示模型换思路不能覆盖用户此前的拒绝。
