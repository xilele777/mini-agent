# Agent Note: 以小而完整的本地 CLI 为完善版 v1 目标

Status: proposed

## Problem

mini-agent 已具备原生工具调用、流式协议组装、权限确认、上下文裁剪、显式出口、todo、同步只读子 Agent 和确定性主轮测试，足以说明 Agent 的核心运行机制。但它仍缺少会话恢复、统一配置诊断、真实上下文预算、安全增量编辑、端到端取消、结构化运行轨迹和可交付 CLI 等产品基本面。

如果继续按“想到什么功能就加什么”的方式推进，项目容易在并行 Agent、RAG、插件系统和更多工具之间膨胀，反而掩盖已经形成的清晰内核。若停在当前状态，它又更像完成度较高的教学样例，还不足以长期作为个人编码助手使用，也不能完整展示一名 Agent 实习生对可靠性、安全、状态和评测的工程理解。

## Proposal

完善版 v1 的目标是：实现一个微型、功能完整、小而美、能够落地、细节精致但不庞大不冗余，并且可以作为 Agent 实习作品、在常见失败条件下仍然抗打的本地 CLI Agent。

“功能完整”指核心工作链闭合，而不是功能数量最大化：用户可以安装与诊断配置，开始或恢复会话，让 Agent 读取、搜索、安全编辑和执行命令，观察明确的批准与运行轨迹，在长上下文、网络失败、命令超时或进程退出后得到可解释的结果，并通过自动测试和少量真实模型场景验证关键行为。

### Product boundary

v1 保持以下边界：

- 单用户、单进程、单项目根目录的本地 CLI，不建立服务端、Web UI 或多租户体系。
- 继续直接使用 OpenAI-compatible SDK、原生 Function Calling、Zod 和显式工具注册表，不引入 LangChain、LlamaIndex 或通用工作流框架。
- 主 Agent 保持单轮顺序执行；现有同步只读子 Agent 足以展示上下文隔离和能力收窄，v1 不增加并行、递归委派或分布式调度。
- 状态使用可检查的本地文件和原子替换，不引入数据库；配置、会话、轨迹和 todo 各有明确所有者，不共享隐式全局状态。
- 新抽象必须服务于一个已经存在的失败边界、去除真实重复或建立可测试接口；不为未来插件、供应商或部署形态预建框架。
- 自动测试负责确定性协议和状态边界，真实模型评测只覆盖少量关键工作流，不把模型措辞当作稳定快照。

### Roadmap

按依赖顺序完成六个阶段，每个阶段都有可单独检查的交付物；恢复、取消和预算遵循下文的共同约定，不把阶段理解为互不相关的模块：

1. **阶段 10：统一配置与启动诊断** — 集中解析模型、base URL、shell、超时和预算；提供不泄露密钥的 doctor。阶段结束前确定取消信号、运行结果和预算归属的最小约定，定义贯穿后续阶段的任务夹具，并将现有确定性检查接入基础 CI；不提前建设完整运行框架。
2. **阶段 11：会话持久化与恢复** — 保存带格式版本、项目绑定、完整历史、轮边界和会话 todo 的原子快照，支持新建、列出和恢复。保留已执行动作及中断状态，结果不确定时先核查；恢复不自动重放工具。损坏或不兼容文件隔离处理，不静默覆盖。
3. **阶段 12：上下文预算与压缩** — 先实现每次请求前的预算检查、完整旧轮裁剪与超限停止，再增加可持久化摘要。原始历史与发送给模型的上下文分离；覆盖当前轮过长、工具定义开销、输出预留和摘要失败，不只处理历史轮数。
4. **阶段 13：安全增量编辑与命令执行** — 增加精确旧文本、文件指纹、原子替换和 diff 预览，批准后执行前重新检查冲突；收紧旧写入入口并统一文件工具的项目边界。接入共同取消信号，在支持的 shell 环境验证命令超时、取消和子进程树清理。
5. **阶段 14：运行韧性与可观测性** — 验证取消贯穿输入、批准、主／子 Agent、摘要、模型请求和工具；整合有限传输重试、全轮次数／时间／token 预算，以及从类型化事件生成的终端输出和脱敏 JSONL 轨迹。沿用前面阶段的生命周期约定，不在此时重新定义状态归属。
6. **阶段 15：评测与交付收尾** — 汇总各阶段已经积累的模拟流、故障注入和真实模型证据，完成新环境安装、CLI 参数、帮助、退出码、README、跨平台 shell 配置与可执行入口验收；形成可克隆、可诊断、可运行、可恢复的 v1。

每个阶段开始时再为其中的非平凡机制建立或更新所属决策笔记；本路线固定目标、顺序和跨模块行为保证，具体接口、文件布局和算法留给所属阶段。测试随模块进入常驻回归，阶段 15 不承担补建全部测试的工作。

### Session recovery and state ownership

原子替换只保护单份状态文件，不会把文件修改、shell 命令和会话保存变成一个事务。当前[异常恢复规则](../../implemented/bug-fix/2026-09-06-tool-result-history-recovery.md)会回退本轮消息而保留外部副作用；阶段 11 必须调整这一规则，不能直接把回退后的“干净历史”当成完整恢复依据。

- 会话绑定规范化的项目根目录并保存格式版本；从其他目录打开时明确报告不匹配，不把历史中的相对路径自动解释到新项目。未知版本和损坏内容不得作为空会话覆盖。v1 不支持同一会话的多个写入者，发现已被占用时拒绝再次写入。
- 原始历史是恢复与核查的依据；供模型使用的裁剪历史和摘要是派生视图，不能覆盖原始历史。摘要应标明覆盖范围，恢复时不能重复拼入已经被摘要覆盖的旧消息。
- todo 随会话保存，新建会话不继承其他会话的任务。旧项目级 `.mini-agent-todo.json` 保留并提示存在，不默默复制进每个新会话。批准缓存保持进程内有效，切换会话时清空，不写入快照；配置和密钥不随对话恢复。
- 在有副作用的工具执行前，先可靠保存调用身份、参数和待执行记录；保存失败就不执行。工具返回后保存已确认结果，再继续后续动作。执行中崩溃，或执行后结果尚未可靠保存，恢复时均按“结果不确定”处理，不能猜测为成功或未执行。
- 恢复先展示中断位置、已确认动作和待核查动作，等待用户继续；不能自动重放未完成调用。继续前核查可观察的外部状态，无法核查的结果如实保留不确定性。协议缺失项可以补为明确的未执行／结果不确定说明，但不得伪造成功结果。

恢复记录只需表达调用与结果的最小事实，不要求提前实现完整 JSONL 轨迹或事件溯源系统。v1 不承诺任意外部命令恰好执行一次，也不承诺自动撤销副作用。

### Runtime lifecycle and budgets

阶段 10 确定约定，后续阶段按实际需要接入：每个真实用户轮由入口创建取消控制器，主 Agent、子 Agent、摘要请求、批准等待及工具接收同一取消信号。取消后不再安排新动作，收尾记录已完成与不确定的结果；取消和超时都不表示已撤销副作用。

运行结果区分完成、暂停、取消、失败和预算耗尽，供 CLI、会话保存和轨迹共同使用，不能只靠终端文本猜测，也不能把所有工具异常都转成可继续执行的普通字符串。具体类型由实现阶段确定；取消必须能传播到调度边界。

单次上下文窗口与整轮累计消耗分别配置和检查。整轮预算覆盖主请求、委派、摘要与重试；子 Agent 仍可有更小的局部上限，但不得绕过总上限。摘要和子 Agent 最终总结也必须先取得预算，不能耗尽后再额外请求。usage 缺失时标注未知或估算，不记为零；时间与请求次数仍提供确定的停止边界。

重试由一个明确的层负责，配置时核对 SDK 自带重试，避免与外层重试叠加。只重试尚未产生可见输出和本次工具执行的可重试传输失败，不重跑整轮；协议错误、权限拒绝和结果不确定的工具执行不得自动重试。

阶段 10 先固定以下语义，后续按所属阶段接入，不提前增加尚无消费者的运行时类型：

| 共同约定 | 具体语义与所有者 | 接入阶段 |
| --- | --- | --- |
| 用户轮身份 | 入口为每次真实用户输入创建 turnId；委派、摘要、重试保留所属 turnId，子任务另有自己的标识 | 11 起 |
| 完成结果 | completed、paused、cancelled、failed、budget_exhausted 分开保存；循环守卫中止属于 failed 并记录原因；只有完成出口属于 completed，不等同于外部验收通过 | 11 起 |
| 取消归属 | 入口持有本轮 AbortController，子流程只接收信号；取消中止当前等待并阻止后续动作；等待下一条用户输入属于 CLI 生命周期，不伪造用户轮 | 13–14 |
| 请求与时间 | 当前 10／6 为主／子循环局部上限；总预算由同一用户轮持有，请求发送前预留次数，每次真实传输尝试计数，包括失败和重试 | 12 起，14 汇总 |
| 总时限 | 按单调时钟从用户提交起计时，包含批准等待；批准返回后仍需检查取消与剩余时间，已过期的动作不能开始执行 | 13–14 |
| token 账目 | 每次发送前检查输入估算与输出预留，响应后结算实际 usage；缺失 usage 保留估算／未知标记，不宣称精确费用硬上限；摘要和委派共享总额 | 12 起，14 汇总 |
| 收尾与恢复 | 确认完成的动作保留结果，未开始的动作标记未执行，执行结果未确认的动作标记不确定；记录失败后不再继续发起副作用 | 11 起 |

配置与 doctor 的当前实现仅有局部请求次数和单请求超时，上述跨轮记录与全轮信号不是已实现能力。固定任务与 CI 的落地边界见[夹具与 CI 决定](../../implemented/testing/2026-09-21-repeatable-fixture-and-ci.md)。

### Context budget and compaction

在主 Agent、子 Agent 和摘要的每次模型请求前计算输入预算，包含 system、工具定义、历史、当前输入和消息协议开销，并预留输出空间。已知模型使用适配的计数方法；未知兼容模型采用明确标注的保守估算和余量，不把估算称为服务端 token 硬保证。上下文超限响应有明确处理，不能无变化地无限重试。

阶段 12 先实现确定性裁剪：只移除完整旧用户轮，保护工具调用与结果配对，不把内部提示当成用户新轮。若裁掉旧轮后，当前轮、单次输入或工具定义仍超限，则停止并提示缩小任务；不发送已知超限的请求，也不强行切断当前工具配对。v1 无需为了处理所有超长任务实现任意位置的轮内压缩。

之后增加旧轮摘要，保留当前目标、用户约束、已确认动作、拒绝与待核查事项；摘要作为有来源的上下文材料，不提升为新的系统权限。摘要请求本身也受窗口和整轮预算限制。生成、校验或保存失败时保持原状态；仅在裁剪后的上下文仍满足约束时继续，否则明确停止，不循环发起摘要。原始历史持续保留，压缩只改变模型请求视图。

### Edit approval and filesystem boundary

增量编辑要求旧文本精确且唯一匹配，并针对读取到的文件版本生成候选内容与可读 diff。批准绑定项目内目标、基准指纹和候选修改；执行前再次核对路径与文件指纹。批准等待期间文件发生变化时拒绝写入，重新读取、生成 diff 并重新批准，不把旧批准应用到新版本。冲突拒绝不能退化为整文件覆盖。

v1 将 `write_file` 限定为创建新文件，已有文件通过增量编辑修改；创建时仍需批准，并拒绝覆盖批准后出现的同名文件。新建与编辑共同检查项目边界、敏感路径及链接目标；新建文件还需检查已有父目录的真实路径。原子替换保证单文件写入完整，不意味着多个文件修改构成事务，也不能替代冲突检查。

项目路径约束针对受控文件工具。批准后的 shell 仍可访问操作系统允许的范围，预览需显示实际工作目录、shell 和完整命令，不宣称获得沙箱隔离。子进程清理以明确支持的系统／shell 组合验收；不能确认后代进程已结束时如实报告，不能仅凭发送了终止信号就宣称清理成功。

### End-to-end task and incremental evaluation

阶段 10 定义一个可重置的小型 TypeScript 示例仓库：包含一个可复现缺陷、能揭示该缺陷的测试和应保持不变的无关文件。先记录当前能力与失败点，后续阶段沿用同一任务，避免每次只挑新功能容易成功的演示。

主任务链为：定位缺陷 → 阅读证据 → 展示 diff 并取得批准 → 修改 → 执行测试 → 按实际结果总结。以预期文件变化、目标测试、原有回归及无关文件未改作为成功依据；调用 `finish_task` 或声称成功不构成验收证据。

| 场景 | 可检查的结果 | 主要引入阶段 |
| --- | --- | --- |
| 配置与基线 | 缺配置、错误 API 路径和不可用 shell 可诊断；现有确定性检查进入 CI | 10 |
| 中断恢复 | 工具开始前、执行中、执行后保存前注入故障；恢复不自动重放、不把未知结果当成功，损坏快照不覆盖上一份可用状态 | 11 |
| 长上下文 | 旧轮压缩、当前轮单独超限、摘要失败均有明确结果；每次请求视图合法，原始历史仍可查 | 12 |
| 编辑与拒绝 | 主任务产生预期 diff；拒绝后目标动作不执行；重复匹配和批准后文件变化均不写入 | 13 |
| 取消与超时 | 输入／批准等待、模型流、委派和运行中命令可以取消；取消后不启动后续工具，支持环境下验证后代进程清理 | 13–14 |
| 重试与总预算 | 传输重试不重放此前动作；主请求、委派、摘要、重试统一计数；预算耗尽明确停止 | 14 |
| 干净环境交付 | Windows 主环境完成安装、doctor、主任务和恢复；Linux 完成配置与非交互检查 | 15 |

故障窗口和状态边界优先用确定性模拟、临时目录和受控子进程验证；不依赖真实模型恰好在某个时刻失败。真实模型逐阶段补普通任务、拒绝、恢复、长上下文与只读委派的使用证据，并记录模型／配置、任务结果、错误修改、请求数、token、耗时和人工干预。重复次数在评测前确定，保留失败记录，不把挑选出的成功运行当成成功率。

v1 交付要求上述确定性验收全部通过、主任务及列出的真实工作流均有可核对的通过记录；成本和耗时先给出测量值，不预设缺乏基线的性能承诺。这些场景是有限能力证据，不代表任意仓库与任务都能成功。

### Explicit non-goals for v1

- 完整操作系统或容器沙箱；v1 明确展示批准与边界，但不宣称能安全执行任意不可信命令。
- GUI、IDE 插件、远程服务、多用户或跨设备同步。
- 并行／递归多 Agent、结构化任务图、工作流引擎和分布式队列。
- 向量数据库、RAG、长期知识库、模型路由和自动供应商切换。
- MCP／插件市场或允许第三方代码任意扩展工具的运行时平台。

这些方向只有在 v1 的真实使用证据表明现有边界成为瓶颈时才重新评估。

## Alternatives considered

- 停在当前教学内核：代码最少，核心原理也已经完整，但对话不能恢复、配置和失败诊断较弱，无法达到“能够落地并长期使用”的目标。
- 追求 Claude Code 的功能广度：并行 Agent、IDE、远程服务、插件、RAG 和完整沙箱会更强，但需要完全不同的产品与安全工程规模，不符合微型和实习作品的边界。
- 尽早迁移到 Agent 框架：会快速获得持久化、回调和工具封装，但关键控制流与失败语义被框架隐藏，削弱该项目展示底层理解和工程判断的价值。
- 先建设通用插件或工作流平台：未来扩展成本可能降低，但当前只有一个主 Agent 和一个只读子 Agent，抽象对象不足；会先产生配置、生命周期和兼容负担，再等待可能不会出现的需求。
- 只在完整用户轮结束后保存快照：写盘少、历史天然易于配对，但轮中已有副作用而结果未保存时无法给出可靠恢复说明；v1 增加副作用前后的最小记录，接受额外写盘和不确定状态处理。
- 先建完整事件溯源与通用执行框架：可统一恢复和轨迹，但会提前冻结所有模块接口；v1 先约定取消、结果和预算归属，恢复用最小动作记录，完整轨迹在阶段 14 整合。
- 首先实现模型摘要以保留更多上下文：长对话信息利用更灵活，但同时引入请求成本、摘要失真和失败恢复；先建立确定性预算边界，再加入摘要，便于分别验证。
- 保留可覆盖任意已有文件的 `write_file`：调用简单，也适合整份生成，但会成为绕过精确编辑与冲突检查的入口；v1 用它创建文件，已有文件统一走受控编辑，接受复杂重写需要拆分修改的代价。

## Acceptance criteria

- 新机器在安装依赖后，可以通过单一 doctor 命令定位缺少的配置、错误的兼容 API 地址或不可用 shell，且任何输出不包含密钥。
- 用户可以新建、退出并恢复绑定项目的会话；todo 随会话隔离，批准不跨恢复继承。保存失败或部分写入不破坏上一份可用快照，未知版本和损坏内容不静默覆盖，第二个写入者不能覆盖同一会话。
- 副作用发生后的失败不能仅以丢弃本轮消息处理；已确认动作与结果不确定动作可区分，恢复不自动重放工具，残缺工具调用不会进入下一次模型请求。中断故障窗口按上表验收。
- 每次主／子 Agent 和摘要请求均检查完整输入与输出预留；旧轮裁剪、单轮超限和摘要失败有确定行为。摘要不破坏调用配对或真实轮边界，原始历史保持可核查。
- 受控文件工具限制在项目边界内；增量编辑具有唯一匹配、指纹检查、原子替换和可读 diff，批准后出现冲突不写入，旧写入入口不能绕过保护。命令可批准、超时、取消，并如实报告副作用和清理结果。
- 完成、暂停、取消、失败和预算耗尽可区分；取消贯穿交互等待、主／子 Agent、摘要、模型请求和工具。传输重试有限且不叠加隐式重试，不重放已经执行的动作。
- 每轮可以查看脱敏的请求数、工具调用、耗时和 token 汇总，缺失 usage 不伪装为零；委派、摘要和重试计入整轮预算。确定性回归与真实模型评测随阶段累积，主任务成功由文件和测试证明。
- CLI 帮助、配置说明、工具列表和项目结构与当前实现一致；Windows 为主要验收环境，Linux 至少具备可配置 shell 和非交互自动检查。
- v1 完成时仍保持单进程本地 CLI、直接 SDK、显式注册表和同步只读子 Agent；没有为了“完整”引入非目标中的平台能力。

## Risks

会话和轨迹可能包含源码、命令输出和模型回复，必须默认保存在本地、明确路径并提供清理方式；日志脱敏不能被描述成绝对不会泄密。

摘要压缩会引入信息损失和额外模型请求，必须保留原始持久化历史或可恢复快照，并用测试保护轮边界。重试若与流式输出或副作用混合，可能导致重复动作，因此只允许在明确尚未产生可见结果和副作用的传输阶段发生。

副作用前后写盘增加 IO 与失败处理；完整历史持续增长，需明确保留和清理方式，不能把单次 prompt 有界等同于磁盘占用有界。原子替换的进程中断保障不自动等于断电持久性保证，具体写盘协议及支持范围由阶段 11 说明和验证。

文件指纹和路径复查用于检测通常的外部修改，无法单独构成抵御恶意并发文件系统变更的完整隔离。Windows／Git Bash 的后代进程清理与其他系统存在差异，必须在声明支持的环境实测，不能仅用 mock 推断。恢复时遇到不可核查副作用需要人工判断，这是保持实现规模可控的代价。

“小而美”容易在阶段推进中被新想法侵蚀。每项新增能力都要回答它关闭了哪个 v1 验收缺口；不能回答时留在非目标列表，而不是顺手加入主线。
